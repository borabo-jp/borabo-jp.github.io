Amazon Ads · Desktop App

Replacing a 211,000-line Excel macro with a tested campaign generator

A Windows desktop app that turns a spreadsheet of products and keywords into upload-ready Amazon Sponsored Products bulk files — built as a faithful, testable reimplementation of a legacy VBA workbook.

  • Electron
  • React
  • TypeScript
  • Vite
  • 510 automated test cases
  • 1,315 gap keywords surfaced in one import
  • 5 parallel campaign types generated per product

Context

Built for an Amazon Ads media-buying operation that generates Sponsored Products campaigns for its client accounts. The output is a bulk file: a spreadsheet formatted to Amazon's exact column rules that gets uploaded directly into Seller Central or the Ads console. Getting that file right the first time matters — a malformed row either fails the upload or, worse, uploads wrong.

The problem

The process this replaced lived entirely inside one Excel workbook, driven by roughly 211,000 lines of extracted VBA macro code. The workbook was simultaneously the data entry surface, the business logic, and the output — product lists, keyword lists, and the campaign-building rules all lived in the same live working file. Changing a rule meant editing the macro that also held the data. There was no separation between what you typed and what ran.

What I built

The app takes three input grids — products, keywords, and a search-term gap tab — and expands each product into the full row stack Amazon's bulk format requires: campaign, bid adjustments, ad group, product ad, and keyword or target rows, plus negatives. It does this across five parallel campaign types per product: Auto, Broad, Phrase, Exact, and product-page targeting, which itself splits into self, competitor, and brand-reinforcement variants.

The search-term gap tab ingests a real Amazon search term report and mines converting terms the account is not yet bidding on, generating product and keyword rows with computed bids. One documented import surfaced 1,315 gap keywords in a single pass. Before anything is exported, 8 hard validation rules and 6 export warnings check budget floors, bid floors, date format, the 120-character campaign-name limit, and dangling product references.

The app is deliberately stateless: no database, no save file. Everything lives in memory for the session, with a template import/export round trip and a crash-recovery snapshot as the only persistence. Export runs through ExcelJS for .xlsx or a hand-written RFC 4180 encoder for .csv. The SKU column is forced to text format on export — ported directly from the legacy tool's number-format directive — so Excel cannot silently render a numeric-looking SKU in scientific notation.

The migration

This is a port, not a rewrite from a blank page, and the distinction shaped every decision. The generation engine follows the legacy VBA's main per-product loop and preserves its exact processing order, so parity tests can assert directly on row order against the old tool's output. That constraint made the port harder to write than a clean-room version would have been, and it is also why the port could be trusted.

Where the legacy behaviour had a known bug that other parts of the system had quietly come to depend on, I kept the bug rather than fix it. Exact-match campaigns get no negative keywords at all, because the legacy tool had a suppression bug there and fixing it now would change live campaign behaviour in a way nobody asked for. That asymmetry is documented in the migration flowchart, not left for the next person to rediscover by accident.

Licensing

The app is self-hosted and distributed as an unsigned portable Windows executable, so it needed its own device gate rather than relying on a platform's license server. The gate is checked before any window or IPC channel exists, and it is built with dependency injection so the whole policy can be unit tested with no Electron process, no filesystem, and no real clock.

It fails closed in every direction I could think to test. An allow-list that is empty but readable means "matches nobody," not "check disabled" — an accidentally cleared sheet locks everyone out rather than unlocking the team. A 14-day offline grace period is backed by a local cache that is bound to the machine's hostname, so copying the cache file to another machine grants nothing. A clock rolled backward, or a corrupted timestamp, fails closed rather than manufacturing extra grace. The allow-list's path is hard-coded and deliberately kept out of user preferences, because a lock a user can repoint is not a lock. And a thrown error anywhere inside the gate is caught and treated as a block, never as allowed-by-default.

Result

  • Campaign rules live in versioned, tested code instead of inside the same file as the product data — a rule change is a code change and a test run, not a search through 211,000 lines of macro.
  • A crash-recovery snapshot recovers in-progress work after a session crash.
  • The generation engine's row order is asserted by parity tests against the legacy tool's output, so a future refactor can't quietly break the parent-child structure a bulk upload depends on — a campaign row still has to precede its own ad group, product ad, and keyword rows.
  • Search-term gap mining turns a raw Amazon search term report into ready-to-review keyword and product rows with computed bids.
  • Every export passes through the same 8 validation rules and 6 export warnings before it reaches Amazon, regardless of who is generating the file.
