Catching catalog problems automatically instead of stumbling into them

A scheduled Cloud Run and BigQuery service that diffs today's catalog state against a rolling history snapshot and emails a grouped digest of what actually changed — account health, inventory, buy box, and listing status — instead of leaving those issues to be found by whoever happens to look.

  • Python
  • BigQuery
  • Cloud Run
  • Cloud Scheduler
  • 5 independent diff rules
  • 29 pytest tests, all behavioural
  • <2s full test suite runtime

Context

A third-party report-ingestion tool lands Amazon Selling Partner API catalog data in BigQuery: account health signals, inventory status, buy box standing, and listing state. The data arrives; nobody was watching it. Every prior tool in this portfolio runs on Electron and VBA-adjacent Windows automation — this one is the odd stack out on purpose, a Python service running on Cloud Run rather than a desktop app, built to prove the same engineering habits (pure functions, tested rules, failure isolation) carry over to a different platform. It's currently a pilot on a single seller account with three subscribed recipients, not a fleet-wide rollout.

The problem

Catalog state changes silently. An account health flag, a listing sliding from active to blocked, inventory going stranded or unfulfillable, a buy box lost — none of it announces itself. Someone has to go look, and by the time they do, the change is old news. The underlying API data doesn't make that easier: account health in particular arrives as a deeply nested, semi-structured report, with single-element array envelopes wrapping fields that should just be scalars, and one identifier column that is reliably null and has to be joined in from a different report entirely. A digest that's supposed to be readable has to get past that shape first.

What I built

A Cloud Scheduler job hits a Cloud Run HTTP endpoint on a cron, authenticated by OIDC rather than a static secret. The service pulls today's catalog snapshot from BigQuery, compares it against a rolling history table, and runs five independent diff rules over the result: account health, unfulfillable inventory, stranded inventory, buy box status, and blocked-versus-active listings. Each rule is a pure function — data in, a list of changes out, no I/O inside it — which is what keeps the suite fast to test and easy to reason about. A recursive leaf-diff walker handles the account health report specifically: it unwraps the platform's single-element-array envelopes and strips known-noisy subfields, collapsing what would otherwise be a wall of raw nested output into one human-readable line per real change.

Each of the five categories is wrapped in its own failure boundary: a BigQuery timeout in one cannot take down the other four or block their emails from going out. A completion guard treats a run's window as done only once all five categories have logged a fresh success, so a partial failure gets picked up and retried automatically by the next invocation — no dead-letter queue, no manual replay. A dry-run mode lets a change to the rules get exercised without sending anything. The output is one grouped digest per subscribed recipient, in both HTML and plain text, enriched with a product name and image pulled alongside each change (the real digests carry real product data; nothing from a live account appears here). Secrets — SMTP credentials, the OIDC audience — come from Secret Manager and are injected at deploy time rather than baked into the image.

The less glamorous parts are documented rather than left for the next person to rediscover: the null product-identifier column and the join that works around it, batch-scoped deduplication, and where the pipeline upserts a table versus overwriting it outright — all called out in docstrings at the point where getting it wrong would silently corrupt a digest.

Result

  • Five independent diff rules — account health, unfulfillable inventory, stranded inventory, buy box status, blocked-versus-active listings — run as pure functions, each isolated so one category's failure never blocks the other four.
  • A self-healing idempotency guard means a partial failure is retried automatically by the next scheduled invocation, with no dead-letter queue to manage.
  • A recursive leaf-diff walker turns the account health report's deeply nested, semi-structured shape into one readable line per real change instead of raw output.
  • 29 pytest tests, all behavioural — synthetic dataframes in, exact change and digest objects asserted out — with no BigQuery or SMTP calls; the full suite runs in under two seconds.
  • Honestly scoped: this runs today as a pilot on one seller account with three subscribed recipients. It's evidence of range onto a Python and cloud stack and of the same engineering discipline as the rest of this portfolio, not a claim of fleet-wide deployment.
