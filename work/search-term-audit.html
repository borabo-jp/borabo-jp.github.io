Amazon Ads · Desktop App

Finding where an advertiser bids against themselves — and fixing a zip reader that could hang forever doing it

A desktop tool that detects Amazon Sponsored Products keyword cannibalisation — the same product and shopper search term bid on by two or more of an advertiser's own keywords — built around a hand-written central-directory zip reader that sidesteps a silent infinite-hang defect in standard xlsx readers.

  • Electron
  • React
  • TypeScript
  • ExcelJS
  • 172 automated test cases
  • 24 test files, including a dedicated zip edge-case fixture
  • ~16s to parse a 23.5MB file with 43,000 search-term rows

Context

An Amazon Sponsored Products account can end up bidding against itself: two or more of its own keywords converge on the same product for the same customer search term, so the account's own ads compete against each other in the auction instead of against outside sellers. Finding those overlaps by hand means cross-referencing search-term reports against campaign structure across every ad group in an account, per match type — tedious enough that it rarely gets done consistently across a large fleet of accounts.

The problem

Amazon's bulk exports are the only source for this: a workbook per account, with a search-term sheet showing which keywords triggered which customer queries and a campaign sheet holding every keyword's live state. Detecting cannibalisation means grouping search-term rows by product identifier and customer search term, separately per match type, and flagging any group served by two or more distinct keyword texts — then turning that into something a human can review and something the platform can act on, without misidentifying which live keyword row to pause.

What I built

A desktop scanner that reads an account's bulk export, groups search-term rows by product identifier and customer search term per match type, and flags any group served by two or more distinct keyword texts as cannibalisation. Rows on paused campaigns are dropped before detection and counted separately as excluded, not silently skipped, so the exclusion count is itself part of the audit trail. Cross-file variant grouping maps sibling child products to a shared parent via a CSV synced from BigQuery, so cannibalisation between competing product variants is caught even when their campaigns live in different export files — candidates are pooled across the whole scan before grouping runs.

Detection produces two outputs with different jobs. An Excel report across three sheets is built for human review. A separate upload-ready pause file reproduces each selected keyword's real campaign row exactly as the platform has it, changing only operation, state, and entity — and it's matched by keyword ID, never by name, because identical keyword and match-type pairs can legitimately exist in more than one ad group.

The engineering problem

The bulk exports themselves turned into the hardest part of the project. Amazon writes them with a streaming zip writer that defers each entry's size to a trailing data descriptor rather than declaring it up front in the local header. A naive sequential reader has to scan forward hunting for that descriptor's signature — and if an entry's compressed bytes happen to contain the same byte sequence, the read either truncates or hangs forever, because the error surfaces on the stream itself rather than the async iterator reading it, so the read neither resolves nor rejects. It just stops.

The fix is to read the archive's central directory instead — the end-of-archive index that carries every entry's true offset and size — so nothing is guessed and only the sheets that are actually needed get decompressed. That's paired with a hand-rolled SAX parser over the sheet XML, so memory stays constant regardless of how large a sheet is.

The rest of the performance work follows from that foundation. One worker thread runs per file, from a pool sized to CPU cores minus one, and each file is capped at five minutes so a single bad file can't stall a whole scan. A deliberate second pass only returns to the campaign sheet — which can run to roughly 69,000 rows — after detection has already narrowed down which keyword IDs actually matter, rather than carrying tens of thousands of unusable rows through the app. Tolerant header aliasing resolves the platform's inconsistent header names case- and whitespace-insensitively, so a differently cased export doesn't silently drop a column. Measured end to end, a 23.5MB file with 43,000 search-term rows plus a 147,000-row campaign sheet parses in about 16 seconds.

The migration

The header-alias table is a port of a legacy VBA class module that matched headers by hard-coded exact string comparison, which broke every time the platform varied its casing. But the detection rule itself was changed, not ported: the legacy tool grouped by product and keyword only and never read the customer search term column at all, so it structurally could not perform this audit. It also summed metrics across rows where this implementation keeps every raw row as its own line, preserving detail the old tool discarded. The port explicitly guards against a known, numbered object-reuse defect in the legacy tool that had produced cross-contaminated output rows — a documented bug this version was written not to repeat.

Result

  • The central-directory zip read replaces a class of reads that could hang forever on a byte-sequence collision with one that knows every entry's true offset and size before it decompresses anything.
  • Detection is exact: groups are keyed by product, customer search term, and match type, and cross-file variant grouping catches cannibalisation between sibling products even when their campaigns live in separate export files.
  • The two output artifacts serve different audiences without drifting apart — a three-sheet Excel report for human review, and a pause file matched by keyword ID that reproduces each selected row exactly as the platform has it.
  • 172 test cases across 24 files, including one built specifically to trigger the streaming-zip data-descriptor collision, run against fixtures generated by a committed generator script — the suite never depends on real client data.
  • A 23.5MB file with 43,000 search-term rows and a 147,000-row campaign sheet parses in about 16 seconds.
